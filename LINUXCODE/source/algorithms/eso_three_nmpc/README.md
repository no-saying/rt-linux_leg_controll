# ESO + Three-Axis NMPC

This directory contains the selected roll, pitch, and yaw-wheel NMPC code and
the three-axis controller orchestration. The application binding is
`control_stack/algorithms/control/three_nmpc_adapter.hpp`; it forwards the
RT-Thread ESO disturbance estimate received in AMP `0x12` to the corresponding
axis prediction and calls `DecoupledController::step()`.

RT-Thread owns and runs Global ESO. The retained `GlobalEso` source is a porting
reference; this application binding never updates it and never adds an ESO
torque term after solving.

Board initialization must create the native solver contexts and provide a
`ThreeNmpcInputMapper` that maps the documented AMP state plus local board
signals into each axis's four state and reference values. The mapper must use
the robot's verified joint order and reference semantics. No default mapping
is supplied because those semantics are hardware/model specific.

The adjacent `estimation.*`, `control_pipeline.*`, `state_reconstruction.*`,
and `scheduler.*` sources are retained reference components from the wider
runtime work. They are not part of the selected three-NMPC CMake target and are
not called by the framework application.

The 36-variable condensed QP is solved by acados' dense-QP HPIPM adapter with
BLASFEO. `initialize_decoupled_nmpc()` creates three persistent solver contexts
before the control loop; each cycle updates the QP input and calls the acados
adapter without allocating workspace memory. Only the identity box-constraint
form currently generated by `build_decoupled_nmpc_qp()` is accepted.

The reduced serial-leg axis dynamics are isolated in `serial_leg_dynamics.*`:
that module owns the four-state vector field, torque input gains, defaults, and
state Jacobian. `decoupled_nmpc.*` owns solver lifecycle; `decoupled_nmpc_qp.*`
owns costs, constraints, rollout orchestration, and QP assembly. Existing
dynamics defaults are simulation placeholders, not a geometry-derived or
identified full serial-leg multibody model. Replace them with verified model
parameters without mixing mechanical equations into the QP implementation.

The target links the bundled, pinned acados dense-QP sources, HPIPM, and
BLASFEO through CMake. `tests/test_acados_qp_solver.cpp` checks analytical QP
solutions, bounds, invalid constraint rejection, and all three NMPC callbacks.
Host latency from this test is diagnostic only; real-time acceptance requires
the target board build and measurements.
